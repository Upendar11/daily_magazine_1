Foundations of
Data Warehousing

Before touching Snowflake, you must internalise why data warehouses exist, how they differ from operational databases, and the classic layered architecture that gives them structure.

"A data warehouse is not just a big database — it is a purpose-built analytics engine where history is preserved, data is integrated, and the only transactions are reads."

Core DW Principle

What Is a Data Warehouse?

Subject-oriented, integrated, non-volatile, time-variant

"A frozen lake — the operational world is a rushing river; the warehouse captures it and keeps it still so you can study it."

The Three Layers of a DW

Staging → Integration (Core DW) → Data Mart

"Raw flour → mixed dough → baked bread. Three stages, each adds structure."
Layer Map
  • Staging: raw data dump, no transformation, temp or permanent
  • Core DW / Integration: cleansed, conformed, historical data in 3NF or dimensional model
  • Data Mart: subject-specific subset for one business unit (Sales, Finance, HR)

Chapter 02 / 06

Snowflake Core
Architecture

Snowflake's three-layer separation of storage, compute, and cloud services is the single most important architectural insight. Everything else flows from it.

05 · Architecture

Snowflake's Three-Layer Architecture

Storage · Compute · Cloud Services — all separate

"Three independent engines sharing one data lake — like a power grid where generators, transformers, and smart meters are all separate but coordinated."
The Three Layers
  • Cloud Services Layer: authentication, query parsing, optimizer, metadata — always on, no charge per query
  • Compute Layer (Virtual Warehouses): MPP clusters that do the heavy lifting — scale independently, you pay per second
  • Storage Layer: columnar compressed data in cloud object storage (S3/GCS/Azure Blob) — pay for GB stored, shared by all VWs
Before → After
BeforeScaling a DB means scaling storage AND compute together.
AfterIn Snowflake, storage and compute scale independently — add VWs without copying data.
Retrieval Keys
Separation of Storage & Compute MPP Virtual Warehouse Cloud Services Metadata
Cloud Services charges kick in only if usage exceeds 10% of daily compute credits — don't panic about metadata queries.

Chapter 03 / 06

Dimensional
Modeling

Ralph Kimball's dimensional modeling is the grammar of analytics databases. Master fact tables, dimension tables, and the art of choosing the right keys.

"A fact table measures what happened. A dimension table describes the context of what happened. Together, they answer every business question."

Kimball Principle
07 · Dim Modeling

Dimensional Modeling Basics

Facts + Dimensions = Analytics power

"A sales receipt: the amount is the fact. Customer, product, date, store are the dimensions that give it meaning."
Core Concepts
  • Grain: the finest level of detail a fact row represents — define this first
  • Measure: numeric, additive quantities in the fact table (revenue, qty)
  • Conformed dimension: same dimension shared across multiple star schemas
Grain must be declared before designing the fact table — changing it later breaks everything downstream.
A fact table is like a spreadsheet of events. Each column that describes the event is a dimension; each column that measures it is a fact.

08 · Fact Types

Three Types of Fact Tables

Transaction · Periodic Snapshot · Accumulating Snapshot

"Transaction: the moment it happened. Periodic: end-of-month balance sheet. Accumulating: order lifecycle from cart to delivery."
TypeGrainExample
TransactionalOne event rowEach sale, each click
Periodic SnapshotPeriod end stateMonthly account balance
Accumulating SnapshotOne row per pipelineOrder: placed→shipped→delivered
Accumulating snapshots are updated in-place as the process advances — the only fact type where rows get modified.

09 · Dim Types

Special Dimension Types

Degenerate · Junk · Role-Playing · Conformed

"Junk dimension is the catch-all drawer — toss all those low-cardinality flags in one place."
Types at a Glance
  • Degenerate: dimension attribute stored IN the fact table (order number, invoice ID)
  • Junk: combine multiple low-cardinality flags/indicators into one small dimension
  • Role-Playing: one date dim used as Order Date, Ship Date, Return Date
  • Conformed: shared dimension used identically across multiple fact tables
Role-playing dimensions use aliases/views — never duplicate the physical table just to play a different role.

10 · Keys

Natural Keys vs Surrogate Keys

Business ID vs System-generated sequence

"Natural key = your passport number (real-world ID). Surrogate key = your row number in the warehouse database."
Before → After
BeforeUse the source system's ID as the DW primary key — it's already unique.
AfterUse surrogate keys in dims — they insulate history from source changes and support SCD Type 2 multiple rows per entity.
Retrieval Keys
Surrogate = system-generated int Natural = business ID SCD support
Always keep the natural key in the dim table as a non-PK column — you still need to match incoming records from source.

SCD Strategies
& Data Loading

Slowly Changing Dimensions are the heartbeat of historical data integrity. Pair them with Snowflake's Stage and COPY INTO mechanics and you have a production-grade loading pipeline.

11 · SCD Types

Slowly Changing Dimensions — All Four Types

How do you handle a customer moving cities? It depends on your history requirement.

"Customer moves from NYC to LA. Do you overwrite, add a row, add a column, or combine? Your choice defines how much history you keep."
TypeStrategyHistory?Use When
Type 1Overwrite old value❌ LostCorrections, no history needed
Type 2New row + effective dates + is_current flag✅ FullMost dims needing full history
Type 3Add prev_value column⚠️ One version backSoft changes, limited history
Type 6Type 1 + 2 + 3 hybrid (current_value col + full rows)✅ Full + current easy accessBest of all worlds, complex ETL
Type 2 Row Example
-- Each version of a customer gets its own surrogate key row
customer_sk | customer_nk | city    | start_dt   | end_dt     | is_current
1001        | CUST-99     | New York| 2020-01-01 | 2023-05-14 | FALSE
1089        | CUST-99     | LA      | 2023-05-15 | 9999-12-31 | TRUE
Before → After
BeforeOverwrite dimension values — new data is correct, old reports stay the same.
AfterType 2 preserves history so old sales always point to the customer's state at transaction time.
Type 2 explodes row count over time — always add an is_current flag and index on it for performance. Type 6 adds a current_value column so current-state queries don't need a filter.

12 · Loading

Stage & COPY INTO

Snowflake's two-step bulk load pattern

"Stage is the loading dock. COPY INTO is the forklift that moves goods from dock to warehouse shelf."
Stage Types
  • User Stage (@~): personal, per-user, non-shareable
  • Table Stage (@%table): auto-created per table, single-table use
  • Named Stage (@my_stage): reusable, shareable, best for production
  • External Stage: points to S3/GCS/Azure blob — files stay in cloud storage
COPY INTO Snippet
COPY INTO sales_fact
FROM @my_stage/sales_2024.csv.gz
FILE_FORMAT = (TYPE=CSV FIELD_OPTIONALLY_ENCLOSED_BY='"')
ON_ERROR = 'SKIP_FILE'
PURGE = TRUE;
COPY INTO tracks loaded file metadata — re-loading the same file is a no-op unless you use FORCE=TRUE.

Chapter 05 / 06

Performance &
Operations

Virtual warehouses, caching, clustering keys, storage integrations, and Snowpipe — the levers you pull when queries are slow or pipelines need to be continuous.

"In Snowflake, the result cache is your best friend. The first query pays; everyone who runs the same query within 24 hours gets it free."

Performance Principle
14 · Compute

Virtual Warehouses

Scale Up (size) vs Scale Out (multi-cluster)

"Scale up = hire a stronger worker. Scale out = hire more workers. Both solve slowness, but differently."
Scale Up vs Scale Out
  • Scale Up: XS → S → M → L → XL → 2XL — doubles resources each step, for complex single queries
  • Scale Out (Multi-cluster): 1 → N identical clusters — for concurrent user load, each gets own cluster
  • Auto-suspend: VW suspends after N seconds of inactivity — stops billing
  • Auto-resume: first query wakes VW automatically — cold start ~5 sec
Multi-cluster doesn't make one slow query faster — it handles more users simultaneously. Size up for query speed; scale out for concurrency.
A VW is like renting a compute server by the second. Bigger server = more power. More servers = more users at once.
1 day3 days1 week1 month
15 · Performance

Cache & Clustering Keys

Three caches + micro-partition pruning

"Three layers of shortcuts before Snowflake touches real data. Hit any one and you save time and money."
Three Cache Types
  • Result Cache: exact query result stored 24h in Cloud Services — free reuse if data/query unchanged
  • Local Disk Cache (Data Cache): VW SSD cache of recently scanned micro-partitions — lives as long as VW is up
  • Remote Disk Cache: managed by cloud storage tier for warm data access
Clustering Keys
  • Snowflake auto-clusters data in micro-partitions (16–512 MB each)
  • Declare a clustering key on high-cardinality filter columns (e.g., date, region) to improve pruning
  • Automatic Clustering (AC) maintains the order continuously for an ongoing cost
Don't cluster on low-cardinality columns like boolean flags — pruning won't help. Use high-selectivity columns like date or order_id.

16 · Integration

Storage Integration

Secure, credential-free access to cloud storage

"Instead of hard-coding AWS keys in Snowflake, let Snowflake's IAM role talk directly to S3 — zero credentials stored."
Setup Flow (AWS)
  • 1. CREATE STORAGE INTEGRATION in Snowflake → get STORAGE_AWS_IAM_USER_ARN
  • 2. Create IAM Role in AWS, attach S3 policy, trust Snowflake's ARN
  • 3. Reference integration in external stage — no access keys ever stored in Snowflake
CREATE STORAGE INTEGRATION s3_int
  TYPE = EXTERNAL_STAGE
  STORAGE_PROVIDER = 'S3'
  ENABLED = TRUE
  STORAGE_ALLOWED_LOCATIONS = ('s3://my-bucket/data/');
You MUST update the IAM trust policy with Snowflake's specific STORAGE_AWS_EXTERNAL_ID each time you recreate the integration — the external ID changes.

17 · Ingestion

Snowpipe — Continuous Loading

Event-driven micro-batch ingestion without a VW

"Snowpipe is the conveyor belt that automatically loads files the moment they land in S3 — no scheduler, no waiting."
How It Works
  • File lands in S3 → S3 Event Notification fires → SQS queue → Snowpipe picks up automatically
  • Serverless: Snowflake manages compute — you don't need an active VW
  • You pay per file loaded (files per second billing) vs VW credit per hour
  • Define via: CREATE PIPE mypipe AS COPY INTO …
Snowpipe has near-real-time latency (seconds to minutes) — not millisecond streaming. For true streaming use Kafka Connector or Streaming API.
Snowpipe is like an automated mail sorter — the moment a letter (file) arrives, it automatically puts it in the right box (table) without you doing anything.

Advanced Snowflake
Features

Time Travel, Zero Copy Cloning, Data Sharing, Materialized Views, Dynamic Data Masking, and the nuanced world of Table Types — Snowflake's power features that make it more than just a query engine.

18 · Time Travel

Time Travel

Query historical states without backups

"Time Travel is a DVR for your data — rewind to any point within the retention window without creating a backup."
Key Mechanics
  • Retention: 0–90 days (Standard: 1 day default; Enterprise: up to 90)
  • Query past: AT (TIMESTAMP), BEFORE (STATEMENT), AT (OFFSET)
  • Restore accidentally deleted/altered data within window
SELECT * FROM orders
  AT (TIMESTAMP => '2024-01-15 09:00:00'::TIMESTAMP);

SELECT * FROM orders
  BEFORE (STATEMENT => '<query_id>');
Longer retention = more Fail-safe storage costs. Set DATA_RETENTION_TIME_IN_DAYS=0 for transient tables that don't need history.
1 day3 days1 week1 month
19 · Recovery

UNDROP & Fail-Safe

The safety net below Time Travel

"UNDROP is the 'undo' button. Fail-Safe is the emergency services that Snowflake calls when even undo didn't work."
Two Recovery Layers
  • UNDROP TABLE/SCHEMA/DATABASE: available within Time Travel retention window — self-service
  • Fail-Safe (7 days): after Time Travel expires, Snowflake can recover data — but only via Support ticket, not SQL
DROP TABLE sales_fact; -- oops!
UNDROP TABLE sales_fact; -- saved!
Fail-Safe is a Snowflake-internal backstop — you cannot access it via SQL. Always use Time Travel first; Fail-Safe is a last resort via Support.

21 · Clone

Zero Copy Cloning

Instant copy that shares storage until divergence

"Cloning is like forking a Git repo — instant, free at first, and only costs extra when your copy diverges from the original."
Key Facts
  • Instant: copies metadata only — no data movement at clone time
  • Copy-on-write: new/changed data in clone is stored separately; unchanged data is shared
  • Clone entire databases, schemas, or tables — great for dev/test environments
  • Clones have independent Time Travel and Fail-Safe
CREATE DATABASE dev_db
  CLONE prod_db; -- instant, zero storage cost initially
Cloning doesn't copy grants or privileges — you must re-apply permissions on the cloned object.
Clone is like making a photocopy that shares the original paper — no extra paper used until you write on your copy.

22 · Sharing

Secure Data Sharing

Share live data across accounts with zero copying

"Data Sharing is like giving someone a read-only window into your database — they see live data, but nothing is copied or moved."
How It Works
  • Provider creates a SHARE, adds tables/views/functions
  • Consumer account creates a database FROM SHARE — queries provider's actual data
  • No data egress, no ETL, no latency — always current
  • Snowflake Marketplace: publish shares to any Snowflake account globally
Consumers pay only for compute they use to query the share — the provider's storage is not charged to the consumer. But be careful what you expose in the share's objects.

23 · Views

Materialized Views

Pre-computed, auto-refreshing query results

"A materialized view is a snapshot that Snowflake keeps fresh automatically — query it like a table, get the speed of cached results."
Regular View vs Materialized View
  • Regular view: stored SQL definition, re-executed every query — no storage cost, always fresh
  • Materialized view: physically stored result, auto-refreshed on source change — costs storage + background compute but much faster for complex aggregations
Materialized views have limitations: no JOINs across multiple tables in definition, no non-deterministic functions, no streams. Use for single-table aggregate patterns.

24 · Security

Dynamic Data Masking

Role-based column masking without data duplication

"Same table, same column, different views based on who's asking — analysts see ****-****-1234, admins see the full credit card number."
How It Works
  • Define a masking policy (SQL function returning masked or real value)
  • Apply to one or more columns
  • Snowflake evaluates the policy at query time based on CURRENT_ROLE()
  • No copy of data — masking is dynamic, real-time
CREATE MASKING POLICY mask_ssn AS (val STRING)
  RETURNS STRING ->
  CASE WHEN CURRENT_ROLE() = 'ANALYST'
    THEN 'XXX-XX-' || RIGHT(val,4)
    ELSE val
  END;
Masking policies require Enterprise edition. Apply them at column level — one policy can govern multiple columns but each column can have only one active policy.

25 · CDC

Streams & Tasks

Change Data Capture + scheduled micro-ETL

"A Stream is a change log journal. A Task is the scheduler that processes it on a cron. Together, they build ELT pipelines inside Snowflake."
Stream Concepts
  • Streams track INSERT / UPDATE / DELETE on a source table with METADATA$ACTION, METADATA$ISUPDATE columns
  • Consuming a stream (via DML in a transaction) advances the offset — like a Kafka consumer offset
  • Standard stream: tracks all DML. Append-only stream: tracks only inserts (cheaper)
CREATE STREAM orders_stream ON TABLE orders;
CREATE TASK process_orders
  SCHEDULE = '5 MINUTE'
  WHEN SYSTEM$STREAM_HAS_DATA('orders_stream')
AS
  INSERT INTO orders_staging
  SELECT * FROM orders_stream WHERE METADATA$ACTION='INSERT';
Streams have a staleness window — if not consumed within the Time Travel retention of the source, the stream becomes stale and must be recreated.

26 · Security

RBAC & Snowflake Roles

Role-Based Access Control — the privilege pyramid

"Snowflake's role hierarchy is a tree — ACCOUNTADMIN at the root, custom roles on branches, objects at the leaves."
Built-In Role Hierarchy
  • ACCOUNTADMIN: top — manages billing, network policies, everything
  • SYSADMIN: creates and owns warehouses and databases
  • USERADMIN: manages users and roles only
  • SECURITYADMIN: manages grants and security policies
  • PUBLIC: default role every user has — give minimal privileges here
Never use ACCOUNTADMIN for day-to-day work — create a custom admin role for that. ACCOUNTADMIN can see billing information and should be tightly controlled.
Roles are like job titles. A cashier role can ring sales; a manager role can open the safe. You wear one role at a time, but you can have many roles assigned to you.
