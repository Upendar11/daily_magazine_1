Chapter 01

SELECT · WHERE · ORDER BY

Filtering rows, combining conditions, and sorting results

01
SELECT + WHERE + ORDER BY
Filtering
"WHERE narrows the rows. ORDER BY arranges them. Forget ORDER BY and you answer the question wrong."
Before: Write WHERE conditions and assume the result is sorted.
After: Results from WHERE have no guaranteed order. ORDER BY is always explicit — if the question says "sorted," it must be in the query.
SELECT title, rating
FROM shows
WHERE genre = 'Sci-Fi'
  AND rating > 8.0
ORDER BY rating DESC;
⚠️ Compare numbers without quotes: rating > 8.0 not rating > '8.0'. Quoted numbers trigger string comparison, not numeric.
WHERE = filterAND = both must matchORDER BY DESC
The content team wants Sci-Fi shows rated above 8.0, best first. WHERE picks the rows, ORDER BY sorts them — both are required to fully answer the question.

02
AND vs OR — When Both Conditions Must Hold
Logic
"AND = both gates must open. OR = either gate is enough."
Before: AND and OR are interchangeable — just pick one.
After: AND makes the result set smaller (both conditions required). OR makes it larger (either condition qualifies). Mixing them wrong produces silent wrong answers.
-- AND: must be Sci-Fi AND rated above 8.0
WHERE genre = 'Sci-Fi' AND rating > 8.0

-- OR: either Sci-Fi OR rated above 8.0
WHERE genre = 'Sci-Fi' OR rating > 8.0
⚠️ Boundary values matter: rating > 8.0 excludes exactly 8.0. Use >= if 8.0 should be included.
AND = intersectOR = unionboundary: > vs >=
If the challenge says "Sci-Fi AND rated above 8.0" — Midnight Frequencies (8.0) is excluded because 8.0 is not strictly greater than 8.0.

Chapter 02

NULL Handling & IN

Why = NULL never works, and how IN replaces multiple OR conditions

03
IS NULL — The Only Way to Check Missing Values
NULL
"NULL means unknown. You can't ask 'is unknown equal to unknown?' — you need IS NULL."
Before: WHERE email = NULL finds rows with missing emails.
After: SQL evaluates = NULL as UNKNOWN (not TRUE), so zero rows ever match. Always use IS NULL or IS NOT NULL.
-- ❌ This always returns 0 rows
WHERE email = NULL

-- ✅ Correct
WHERE email IS NULL
WHERE email IS NOT NULL
⚠️ NULLs are also invisible to COUNT(*) vs COUNT(column). COUNT(*) counts all rows; COUNT(email) skips NULLs.
IS NULLIS NOT NULL= NULL → always false
Aisha has no email — it's NULL. email = NULL returns nothing. email IS NULL finds Aisha correctly.

1 day 3 days 1 week 1 month
04
IN — Cleaner Multiple-Value Matching
Filtering
"IN replaces a chain of ORs — cleaner, faster to read, and easier to extend."
Before: Write country = 'USA' OR country = 'Japan' for multiple values.
After: country IN ('USA', 'Japan') does the same thing with less noise. Works for any number of values.
-- OR approach (verbose)
WHERE country = 'USA' OR country = 'Japan'

-- IN approach (clean)
WHERE country IN ('USA', 'Japan')

-- NOT IN: exclude a set
WHERE country NOT IN ('USA', 'Japan')
⚠️ NOT IN breaks silently if the list contains a NULL — use NOT EXISTS or IS NOT NULL guard instead.
IN = OR shorthandNOT IN = exclude setNULL in NOT IN = danger
Finding users from USA, Japan, or Ghana? country IN ('USA','Japan','Ghana') — one clean condition instead of three ORs chained together.

Chapter 03

GROUP BY + Aggregates

Collapsing rows into groups and computing summary statistics

05
GROUP BY — Bundling Rows Together
Aggregation
"GROUP BY folds many rows into one per group. After that, only aggregates can summarize within each group."
Before: SELECT all columns and COUNT() in the same query freely.
After: Once you GROUP BY, every column in SELECT must either be in GROUP BY or wrapped in an aggregate (COUNT, SUM, AVG, MIN, MAX).
SELECT user_id,
       COUNT(completed) AS completed_watches
FROM watch_history
WHERE completed = TRUE
GROUP BY user_id
ORDER BY completed_watches DESC;
⚠️ SQL clause order is strict: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY. WHERE before GROUP BY — always.
GROUP BY = bundleaggregate: COUNT SUM AVGWHERE before GROUP BY
All of Marcus's completed watches get bundled into one row. COUNT() then counts how many rows were in his bundle — that's his total.

06
SQL Clause Execution Order
Fundamentals
"SQL writes left-to-right but executes inside-out. The order of clauses is fixed by the engine, not you."
Before: Write clauses in whatever order feels natural.
After: Logical execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. Writing them wrong causes syntax errors or silent logic bugs.
-- Correct clause order:
SELECT   col, COUNT(*)     -- 5th: what to show
FROM     table              -- 1st: where data is
WHERE    condition          -- 2nd: filter rows
GROUP BY col               -- 3rd: bundle groups
HAVING   COUNT(*) > 1     -- 4th: filter groups
ORDER BY col DESC          -- 6th: sort output
⚠️ This is the most-tested SQL concept in interviews. Memorize it like an alphabet — it never changes.
FROM firstWHERE before GROUP BYHAVING after GROUP BY
Think of building a report: first find your table, filter out bad rows, bundle what's left, filter the bundles, then decide what columns to show and in what order.

Chapter 04

HAVING — Filtering After Grouping

The one clause WHERE can't do — filtering on aggregate results

07
HAVING vs WHERE — The Interview Classic
HAVING
"WHERE filters rows. HAVING filters groups. They can't swap jobs."
Before: Use WHERE to filter on COUNT() or SUM() results.
After: WHERE runs before GROUP BY — it doesn't know what COUNT() will produce. HAVING runs after GROUP BY and sees aggregated results.
-- Find users who watched MORE than 1 show
SELECT user_id, COUNT(watch_id) AS cnt
FROM watch_history
GROUP BY user_id
HAVING COUNT(watch_id) > 1;
-- Decision rule:
-- Raw column value → WHERE
-- Aggregate result (COUNT,SUM,AVG) → HAVING
-- No GROUP BY → no HAVING needed
ClauseFiltersRunsCan use aggregates?
WHEREIndividual rowsBefore GROUP BY❌ No
HAVINGGrouped resultsAfter GROUP BY✅ Yes
HAVING = post-group filterWHERE = pre-group filter
You can't ask "which bucket has more than 5 items?" before you've filled the buckets. HAVING asks the question after GROUP BY has filled them.

Chapter 05

JOINs — Connecting Tables

Finding the bridge table, JOIN types, and multi-table queries

08
JOIN — The Bridge Table Mental Model
JOIN
"When you need data from multiple tables, find the table that holds the foreign keys — that's your bridge. Start there."
Before: Join whichever tables seem closest together.
After: watch_history holds both user_id and show_id — it's the bridge. Start from the bridge, then JOIN outward to users and shows.
SELECT u.name, s.title, w.watched_on
FROM watch_history w
JOIN users u  ON w.user_id = u.user_id
JOIN shows s  ON w.show_id = s.show_id
WHERE w.completed = TRUE;
⚠️ JOIN on the wrong table = zero rows or wrong results. users doesn't have show_id — only watch_history does. Always trace the foreign keys.
bridge tableON = join conditionalias w, u, s
You need the user's name and show's title — but they don't share a table. watch_history is the bridge: it knows which user watched which show.

09
INNER vs LEFT JOIN
JOIN
"INNER JOIN = only matched rows survive. LEFT JOIN = all left-side rows survive, NULLs fill unmatched right-side."
Before: Use INNER JOIN by default — it works for all situations.
After: INNER JOIN hides users with no subscription. LEFT JOIN keeps them with NULL in the plan column. Choose based on whether you want to see the unmatched rows.
-- INNER: only users WITH a subscription
SELECT u.name, s.plan
FROM users u
JOIN subscriptions s ON u.user_id = s.user_id;

-- LEFT: ALL users, NULL plan if no subscription
SELECT u.name, s.plan
FROM users u
LEFT JOIN subscriptions s ON u.user_id = s.user_id;
⚠️ To find users with NO subscription: LEFT JOIN + WHERE s.user_id IS NULL. This is the anti-join pattern.
INNER = intersectionLEFT = preserve leftanti-join = LEFT + IS NULL
You want to see every user even if they have no subscription? LEFT JOIN. You only want users with subscriptions? INNER JOIN.

Chapter 06

CTEs & Subqueries

Writing reusable query blocks and combining result sets

10
Subquery — IN vs EXISTS
Subquery
"IN builds a list then checks membership. EXISTS stops as soon as it finds one match — faster on large tables."
Before: IN and EXISTS are interchangeable — use whichever looks easier.
After: IN returns a full list of values for comparison. EXISTS is a correlated subquery that short-circuits on first match. EXISTS wins on performance for large datasets.
-- IN: subquery in WHERE
SELECT name FROM users
WHERE user_id IN (
  SELECT user_id FROM watch_history
  WHERE completed = TRUE
);

-- EXISTS: correlated subquery
SELECT name FROM users u
WHERE EXISTS (
  SELECT 1 FROM watch_history w
  WHERE w.user_id = u.user_id
    AND w.completed = TRUE
);
⚠️ NOT IN fails silently if the subquery returns any NULLs — prefer NOT EXISTS for safety.
IN = list checkEXISTS = early exitNOT EXISTS = safer than NOT IN
IN: "Is your ID in this list of completers?" EXISTS: "Does even one completion record exist for you?" — same result, different efficiency.

11
CTE — Named Temporary Results
CTE
"A CTE is a subquery with a name. It makes complex queries readable by giving intermediate steps a label."
Before: Nest subquery inside subquery inside subquery.
After: WITH cte_name AS (…) defines a named block you can reference like a table. Multiple CTEs can be chained. Query reads top-to-bottom like a story.
WITH premium_users AS (
  SELECT user_id
  FROM subscriptions
  WHERE plan = 'Premium'
),
completers AS (
  SELECT user_id
  FROM watch_history
  WHERE completed = TRUE
)
SELECT u.name
FROM users u
WHERE u.user_id IN (SELECT user_id FROM premium_users)
  AND u.user_id IN (SELECT user_id FROM completers);
⚠️ CTEs are not always faster than subqueries — some engines materialize them, others inline them. Test before assuming CTE = performance.
WITH name AS (...)chain CTEs with commareadable = maintainable
Instead of one giant nested query, define premium_users and completers separately at the top, then join the simple named blocks together at the bottom.

Chapter 07

Window Functions

RANK, DENSE_RANK, ROW_NUMBER, running totals, and OVER()

12
RANK vs DENSE_RANK vs ROW_NUMBER
Window
"Three ranking functions. One question: what happens when two values tie?"
Before: Use RANK() for all ranking tasks — it's the obvious choice.
After: RANK() = ties share rank, next rank skips. DENSE_RANK() = ties share rank, next rank doesn't skip. ROW_NUMBER() = no ties, always unique sequential number.
SELECT user_id, total_minutes,
  RANK()       OVER (ORDER BY total_minutes DESC) AS rnk,
  DENSE_RANK() OVER (ORDER BY total_minutes DESC) AS dense_rnk,
  ROW_NUMBER() OVER (ORDER BY total_minutes DESC) AS row_num
FROM user_totals;
FunctionTies get...After ties...
ROW_NUMBER()Different numbersContinues 1,2,3,4
RANK()Same numberSkips: 1,1,3
DENSE_RANK()Same numberNo skip: 1,1,2
RANK = skip after tiesDENSE_RANK = no skipROW_NUMBER = always unique
Two people tied for 1st place. RANK: 1, 1, 3. DENSE_RANK: 1, 1, 2. ROW_NUMBER: 1, 2, 3 (one gets lucky, one doesn't).

13
OVER() — The Window Function Anatomy
Window
"OVER() is what makes a function a window function. Without it, SUM() collapses rows. With it, SUM() looks across rows."
Before: SUM() always collapses rows into one total.
After: SUM() OVER (PARTITION BY user_id ORDER BY watched_on) computes a running total per user — without collapsing any rows.
-- Running total per user
SELECT user_id, watched_on, minutes_watched,
  SUM(minutes_watched)
    OVER (PARTITION BY user_id
          ORDER BY watched_on) AS running_total
FROM watch_history;

-- Compare to group average
SELECT user_id, minutes_watched,
  AVG(minutes_watched)
    OVER (PARTITION BY user_id) AS avg_per_user
FROM watch_history;
⚠️ PARTITION BY = "restart the window for each group." ORDER BY inside OVER = "accumulate in this order." Both are optional but powerful.
PARTITION BY = reset per groupORDER BY in OVER = accumulateno GROUP BY needed
OVER() says: "look at these rows as a window, compute something across them, but don't collapse them into one." Each row keeps its own value.

14
CTE + Window Function Pattern
Window
"Aggregate first in a CTE, rank second in the outer query. Two steps, perfectly clean."
Before: Try to GROUP BY and apply RANK() in the same SELECT.
After: Compute totals in the CTE. Apply RANK() OVER in the final SELECT. Two clean layers — easier to debug, easier to extend.
WITH user_totals AS (
  SELECT user_id,
         SUM(minutes_watched) AS total_minutes
  FROM watch_history
  GROUP BY user_id
)
SELECT user_id,
       total_minutes,
       RANK() OVER (ORDER BY total_minutes DESC) AS rnk
FROM user_totals;
⚠️ SUM() ignores NULLs — users with only NULL minutes still appear but get NULL total_minutes. Use COALESCE(SUM(...), 0) to treat them as 0.
CTE = step 1 totalsRANK() OVER = step 2COALESCE for NULLs
First CTE computes total minutes per user. Then RANK() looks at all those totals and assigns 1st, 2nd, 3rd place — ties share their rank.

15
CTE — 5 Patterns to Know
CTE Patterns

1 · Basic CTE

WITH premium AS (
  SELECT user_id FROM subscriptions
  WHERE plan = 'Premium'
)
SELECT name FROM users
WHERE user_id IN
  (SELECT user_id FROM premium);

2 · Chained CTEs

WITH done AS (
  SELECT user_id FROM watch_history
  WHERE completed = TRUE
),
prem AS (
  SELECT user_id FROM subscriptions
  WHERE plan = 'Premium'
)
SELECT name FROM users
WHERE user_id IN (SELECT user_id FROM done)
  AND user_id IN (SELECT user_id FROM prem);

3 · CTE with Aggregation

WITH totals AS (
  SELECT user_id,
    SUM(minutes_watched) AS total_m
  FROM watch_history
  GROUP BY user_id
)
SELECT u.name, t.total_m
FROM users u
JOIN totals t ON u.user_id = t.user_id;

4 · CTE feeding JOIN

WITH active AS (
  SELECT user_id, plan
  FROM subscriptions
  WHERE active = TRUE
)
SELECT u.name, a.plan
FROM users u
JOIN active a ON u.user_id = a.user_id;

5 · CTE with HAVING

WITH wc AS (
  SELECT user_id,
    COUNT(*) AS total
  FROM watch_history
  GROUP BY user_id
  HAVING COUNT(*) > 1
)
SELECT u.name, wc.total
FROM users u
JOIN wc ON u.user_id = wc.user_id;

  COUNT(w.watch_id) AS total

-- Users with NO subscription

FROM users u
LEFT JOIN subscriptions s
  ON u.user_id = s.user_id
