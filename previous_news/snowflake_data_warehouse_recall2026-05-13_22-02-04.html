Chapter 01

Data Warehouse Foundations

DW basics, OLTP vs OLAP, warehouse layers, and Data Lake distinctions

01
What is a Data Warehouse?
DW Basics
"A DW is a library — everything curated, indexed, and optimized for reading, not for updating."
Before: A database and a data warehouse are basically the same thing.
After: A DW is purpose-built for analytical queries — historical, integrated, subject-oriented, non-volatile.
⚠️ Don't say "we store data" — say "we integrate, transform, and serve historical data for analysis."
subject-orientedintegratednon-volatile
Imagine a giant filing cabinet where every department's data is cleaned, organized, and stored forever — just for reports, never for daily operations.

02
OLTP vs OLAP
DW Basics
"OLTP is a cashier ringing up orders. OLAP is the CFO reviewing quarterly trends."
Before: Both handle SQL queries, so they're interchangeable.
After: OLTP = small, fast, transactional writes. OLAP = large, complex, analytical reads across millions of rows.
⚠️ OLTP is normalized (3NF) to avoid redundancy. OLAP is denormalized for fast reads — the opposite goal.
OLTP = writesOLAP = reads3NF vs star
OLTP handles your bank recording a transaction right now. OLAP helps the bank understand all your transactions over 5 years.

03
Data Warehouse Layers
DW Architecture
"Raw → Cleaned → Served. Each layer adds a layer of trust."
Before: Just load data into one big table and query it.
After: Staging (raw) → ODS (operational) → Core/DW (transformed) → Data Mart (subject-specific). Each step adds governance.
⚠️ Never query from staging in production dashboards — it's untransformed, potentially duplicated data.
stagingODSdata mart
Think of it like cooking: first you buy raw groceries (staging), then you prep them (ODS), then you cook the dish (DW), then you plate it (data mart).

1 day 3 days 1 week 1 month
04
Data Lake vs Data Warehouse
DW Basics
"Data Lake = dump it all in a pond. Data Warehouse = fill a curated swimming pool."
Before: Data Lake is just a cheaper Data Warehouse.
After: Lake = schema-on-read, raw, unstructured/semi-structured. DW = schema-on-write, structured, governed, query-optimized.
⚠️ "Data Swamp" happens when a Data Lake has no governance — metadata, cataloging, and access controls are mandatory.
schema-on-readschema-on-writedata swamp
A Data Lake stores everything as-is — photos, files, JSON, CSV. A Data Warehouse only stores clean, organized, structured data ready for questions.

Chapter 02

Snowflake Architecture

How Snowflake separates storage from compute and scales independently

05
Snowflake Overview
Snowflake
"Snowflake is not a database. It's a cloud-native data platform that separates what you store from how you compute."
Before: Snowflake is just another cloud SQL database.
After: Snowflake has 3 layers: Cloud Services (brain), Query Processing (virtual warehouses), and Storage (columnar, S3/Azure/GCS) — all independent.
⚠️ You pay for storage and compute separately — a warehouse sitting idle still costs nothing, unlike traditional databases.
3-layer architecturecolumnar storagemulti-cluster
Snowflake is like renting a kitchen (compute) separately from the pantry (storage) — you only pay for the kitchen when you're actually cooking.

1 day 3 days 1 week 1 month
06
Snowflake's 3-Layer Architecture
Snowflake
"Storage is forever. Compute is on-demand. Cloud Services is always-on intelligence."
Before: All three layers must be scaled together like traditional DBs.
After: Cloud Services (metadata, auth, optimizer) runs always. Virtual Warehouses spin up/down. Storage persists independently in cloud object stores.
⚠️ Cloud Services layer queries (metadata-only, < 10% of credits) don't consume warehouse credits — but heavy queries to it can still be charged.
cloud servicesvirtual warehousecentralized storage
Imagine: a permanent warehouse (storage), a team of workers you hire only when needed (virtual warehouse), and a manager who's always in the office for free (cloud services).

07
Virtual Warehouses & Sizing
Compute
"A Virtual Warehouse is your compute cluster — sizes go XS to 6XL, each doubling in power and cost."
Before: Bigger warehouse = always faster queries.
After: Bigger warehouse speeds up single query execution (scale up). Multi-cluster handles concurrency (scale out). Wrong choice wastes credits.
⚠️ Auto-suspend is your best friend — set it to 60–300 seconds or you'll burn credits on idle compute all day.
scale up vs outauto-suspendcredits/hour
Size is like hiring more workers for one big job. Multi-cluster is like opening more checkout lanes when the store gets busy.

08
Caching & Micro-Partitions
Performance
"Snowflake has 3 caches — each one faster and cheaper than hitting storage."
Before: Every query goes to disk — performance depends only on warehouse size.
After: Result Cache (24h, free) → Local Disk Cache (warehouse SSD) → Remote Storage. Micro-partitions + clustering keys prune irrelevant data automatically.
⚠️ Result cache is invalidated if the underlying data changes — repeated identical queries on changing tables won't cache.
result cachemicro-partitionspartition pruning
If you asked Snowflake the same question yesterday and nothing changed, it hands you the same answer instantly — no work needed.

Chapter 03

Dimensional Modeling

Star schema, fact & dimension tables, surrogate keys, and schema types

09
Dimensional Modeling Basics
Modeling
"Facts measure what happened. Dimensions describe who, what, when, where."
Before: Just normalize everything into 3NF like in OLTP.
After: Dimensional modeling uses Fact tables (metrics, FK references) + Dimension tables (descriptive attributes) for fast, intuitive analytics.
⚠️ Don't put measures in dimension tables or descriptive attributes in fact tables — keep the roles clean.
fact tabledimension tablegrain
A sale happened (fact): $50, 2 items. WHO bought it (customer dimension), WHAT was sold (product dimension), WHEN (date dimension).

10
Star vs Snowflake Schema
Modeling
"Star = simple, fast, some redundancy. Snowflake schema = normalized dimensions, more joins."
Before: Snowflake schema is always better because it's more normalized.
After: Star schema wins for query performance (fewer joins). Snowflake schema reduces redundancy but adds query complexity. Most DWs prefer Star.
⚠️ Don't confuse Snowflake schema (data model) with Snowflake (the cloud platform) — completely different things.
star = denormalizedsnowflake = normalizedjoin depth
Star schema: fact table in the middle, dimension tables around it like a star. Snowflake schema: dimensions are further split into sub-dimensions.

1 day 3 days 1 week 1 month
11
Types of Fact Tables
Modeling
"Transaction = snapshot in time. Periodic = end of period. Accumulating = lifecycle of a process."
Before: There's only one kind of fact table — just rows of events.
After: Transaction (each event), Periodic Snapshot (state at regular intervals), Accumulating Snapshot (one row per process lifecycle, updated as it progresses).
⚠️ Accumulating snapshots violate "append-only" — rows get updated as pipeline stages complete. Design for this explicitly.
transactionperiodic snapshotaccumulating snapshot
Order placed → shipped → delivered: one row in accumulating snapshot, updated at each stage. Monthly inventory: periodic snapshot. Each sale: transaction fact.

1 day 3 days 1 week 1 month
12
Types of Dimension Tables
Modeling
"Conformed = shared. Junk = low-cardinality flags. Degenerate = the order number on the receipt."
Before: Dimensions are just lookup tables with an ID and description.
After: Conformed (shared across facts), Junk (combined flag/indicator dim), Degenerate (key stored directly in fact), Role-playing (same dim used twice with aliases).
⚠️ Role-playing dimensions need VIEW aliases — never physically duplicate the table.
conformedjunkdegenerate
The Date dimension is conformed — used by Sales facts, HR facts, Inventory facts. Order number on a receipt is degenerate — stored in the fact, not its own table.
Spaced Repeat
1 day 3 days 1 week 1 month
13
Natural vs Surrogate Keys
Modeling
"Natural key = the business ID. Surrogate key = the DW's own ID. Always use surrogate keys in DW."
Before: Just use the business ID (email, product code) as the PK — it's already unique.
After: Surrogate keys (auto-generated integers) protect against source system changes, allow SCD tracking, and improve join performance.
⚠️ Never expose surrogate keys to end users — they're internal DW plumbing with no business meaning.
surrogate = system-generatednatural = business keySCD compatibility
Your employee ID is the natural key. The DW assigns its own secret number (surrogate key) so even if the employee ID changes, history is preserved.

Chapter 04

ETL, SCDs & Data Loading

Slowly Changing Dimensions, staging, file formats, and COPY INTO

14
SCD Type 1, 2, 3, 6
SCDs
"Type 1 = overwrite (forget). Type 2 = new row (remember everything). Type 3 = previous column (remember one change). Type 6 = hybrid."
Before: Just update the record when something changes — no need to keep history.
After: Type 1 loses history. Type 2 adds new row with effective dates + is_current flag. Type 3 adds old/new column. Type 6 = 1+2+3 combined.
⚠️ SCD Type 2 requires surrogate keys — you can't have two rows with the same natural key as PK.
effective_dateis_currentexpiry_date
Customer moves cities. Type 1: update city field. Type 2: keep old row, add new row. Type 3: add "previous_city" column. Type 6: all of the above.

15
Stages & COPY INTO
Data Loading
"A Stage is a landing zone. COPY INTO is the loader. Together they replace most ETL tools."
Before: Load files directly from local disk into Snowflake.
After: PUT files → Internal Stage (Snowflake-managed) OR use External Stage (S3/Azure/GCS) → COPY INTO table. Stages are temporary file storage.
⚠️ COPY INTO is idempotent by default (tracks loaded files) — re-running won't duplicate data unless you use FORCE=TRUE.
internal stageexternal stageCOPY INTO
You put your CSV on a loading dock (stage), then tell Snowflake to move it into the warehouse (COPY INTO). Snowflake remembers which files it already loaded.

16
File Formats in Snowflake
Data Loading
"Parquet = columnar, fast analytics. ORC = Hive-optimized. Avro = row-based, schema evolution. CSV = simplest but slowest."
Before: CSV is fine for all data loads — it's universal.
After: Parquet/ORC are 2–10x faster for analytics (columnar compression). Avro supports schema evolution. JSON/XML for semi-structured. CSV for simplicity only.
⚠️ Always create a named FILE FORMAT object in Snowflake — don't inline format options in every COPY INTO statement.
ParquetcolumnarFILE FORMAT object
Parquet stores a column of 1 million prices together, so "total revenue" queries only read prices. CSV reads every field in every row — much slower.

17
Storage Integration
Security
"Storage Integration = the secure handshake between Snowflake and your S3/Azure bucket without embedding credentials."
Before: Pass AWS access key + secret directly in the stage definition.
After: Create STORAGE INTEGRATION object (IAM role trust) → Snowflake gets a managed service account → no secrets in SQL code.
⚠️ Storage Integrations require Account Admin to create — not a task for regular roles.
IAM trust policyno credentials in SQLSTORAGE INTEGRATION
Instead of giving Snowflake a key to your S3 house, you tell AWS "trust this Snowflake agent" — no key is ever passed around.

18
Snowpipe — Continuous Loading
Streaming
"Snowpipe is event-driven COPY INTO — the moment a file lands in S3, it's loaded automatically."
Before: Schedule a COPY INTO job every 15 minutes to check for new files.
After: Snowpipe uses S3 Event Notifications → SQS → Snowpipe auto-ingest. Files loaded within seconds, no scheduled jobs needed.
⚠️ Snowpipe uses serverless compute — billed differently from virtual warehouses. Don't mix up cost models.
auto-ingestSQS notificationserverless billing
Snowpipe watches your S3 bucket. The second a new file appears, it automatically loads it into Snowflake — no one has to push a button.

Advanced Snowflake Features

Time Travel, Undrop, Table Types, Zero Copy Clone, and Data Recovery

19
Time Travel
Recovery
"Time Travel is a DVR for your data — rewind up to 90 days and query what used to be there."
Before: Once you DELETE or UPDATE data, it's gone forever unless you have backups.
After: Snowflake retains historical data for 0–90 days (Standard: 1 day, Enterprise: 90 days). Query with AT/BEFORE TIMESTAMP or OFFSET.
⚠️ Time Travel storage costs money — longer retention = more storage cost. Set DATA_RETENTION_TIME_IN_DAYS thoughtfully per table.
AT TIMESTAMPBEFORE STATEMENTretention days
You accidentally deleted a table. Time Travel lets you go back to yesterday and see exactly what was there — like a database time machine.

20
Fail-Safe & UNDROP
Recovery
"UNDROP is undo for tables. Fail-Safe is the 7-day vault after Time Travel expires."
Before: Dropped tables are gone — only backups can help.
After: UNDROP TABLE/SCHEMA/DATABASE restores within Time Travel window. After TT expires, Fail-Safe gives 7 more days — but only Snowflake Support can access it.
⚠️ You cannot query Fail-Safe data yourself — only Snowflake Support can restore it, and it takes time. Don't rely on Fail-Safe for routine recovery.
UNDROP TABLEfail-safe 7 dayssupport-only access
UNDROP is like Ctrl+Z for tables — instant restore. Fail-Safe is like the backup hard drive your IT department holds — you have to ask them nicely.

1 day 3 days 1 week 1 month
21
Snowflake Table Types
Tables
"Permanent = default, full TT+FS. Transient = lighter, no Fail-Safe. Temporary = session-only, vanishes."
Before: All tables work the same way — just create and use.
After: Permanent (full TT+FS, production), Transient (TT only, no FS, staging/intermediate), Temporary (session-scoped, no TT+FS, dev/testing).
⚠️ Staging tables should be Transient — no need for Fail-Safe on raw data you can reload. Saves storage cost.
permanenttransienttemporary
Permanent is your real furniture. Transient is the rental furniture you use temporarily. Temporary is borrowing a chair — gone when you leave the session.

22
Zero Copy Cloning
Efficiency
"CLONE creates a full copy of a database or table instantly — without duplicating any storage."
Before: Cloning a 10TB database requires 10TB of new storage and hours of copying.
After: Zero Copy Clone shares micro-partitions between source and clone. Only new writes to either copy create additional storage. Clone is instant and nearly free.
⚠️ Cloning doesn't copy privileges — you must re-grant permissions on the cloned object.
shared micro-partitionscopy-on-writeCLONE keyword
Imagine a shortcut on your desktop — it points to the same file, takes no extra space. Only when you edit the copy does a real duplicate get made.

Chapter 06

Power Features

Data Sharing, Materialized Views, and Dynamic Data Masking

23
Snowflake Data Sharing
Sharing
"Share live data across accounts — no ETL, no copies, no lag. Consumers read your data directly."
Before: Share data by exporting files and sending them to partners.
After: CREATE SHARE → grant database objects → consumers create databases from share → they query your live data through their own virtual warehouse. Provider pays for storage, consumer for compute.
⚠️ Shared data is read-only to consumers. They cannot modify or load into the share objects.
CREATE SHAREprovider/consumerno data copy
Like giving someone a key to read your Google Doc — they see live updates instantly, no download needed. You control what they can see.

24
Materialized Views
Performance
"A Materialized View is a pre-computed query result stored as a table — automatically refreshed by Snowflake."
Before: Regular views execute the query on every call — expensive for complex aggregations.
After: Materialized views store the query result. Snowflake auto-refreshes when base table data changes (using background serverless compute). Queries hit the cache.
⚠️ Materialized views have restrictions: no joins on multiple tables in some editions, no non-deterministic functions, no UDFs. Check docs before using.
pre-computedauto-refreshserverless maintenance
Instead of calculating the daily sales total every time someone asks, you pre-calculate and store it. When new sales come in, Snowflake quietly updates the answer.

25
Dynamic Data Masking
Security
"Same table, same query — an analyst sees ***-**-1234, an HR manager sees the full SSN."
Before: Create separate masked views per role — maintain multiple objects as data changes.
After: Create MASKING POLICY with conditional logic → apply to column → Snowflake applies at query time based on current_role(). One object, multiple visibility levels.
⚠️ Masking policies are applied at query time, not storage time — the underlying data is never modified. This is critical for compliance.
MASKING POLICYcurrent_role()column-level security
The same employee table exists once. When a junior analyst queries it, SSNs show as ****. When HR queries it, they see the real numbers — same data, different masks.

26
RBAC & Row Access Policies
Security
"RBAC controls what objects you can touch. Row Access Policies control which rows you can see within those objects."
Before: Use WHERE clauses in views to filter rows by user.
After: RBAC = role hierarchy (ACCOUNTADMIN → SYSADMIN → custom roles). Row Access Policy = centralized row-level filter applied transparently at query time per role/user.
⚠️ Row Access Policies are transparent to users — they don't know rows are being filtered. Document this for auditors.
role hierarchyROW ACCESS POLICYSYSADMIN vs SECURITYADMIN
RBAC is the key card that gets you into a building. Row Access Policy is the office door that only shows you your department's files once you're inside.
